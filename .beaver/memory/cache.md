# cache

## 캐시한 데이터를 바꾸는 쓰기는 그 캐시도 함께 고친다(무효화 전략)
- Rule: 캐시에 올린 데이터의 원본(DB)을 바꾸는 쓰기는 **같은 처리 안에서 그 대상의 캐시 키도 함께 고친다**. 회원 캐시(로그인 회원 확인 auth-user 등)라면 그 회원을 바꾸는 모든 쓰기가 대상이다.
  - 회원 대상 쓰기: 정지 · 정지 해제 · 탈퇴 신청 · 탈퇴 철회 · 탈퇴 완료(scheduler crontab) · 권한 변경 · 정보 수정 · 업체 배정 변경 · 계정 삭제.
  - 다른 캐시 대상(업체 · discovery 등)도 같은 원칙이다.
- 도입 때 확정할 기본안 (Claude 제안 — 캐싱할 곳을 정하는 기획에서 사용자와 확인한다)
  - **고치기 = 키 삭제(cache-aside)** — 다음 조회가 DB 에서 다시 채운다. 새 값을 직접 써 넣는 갱신(write-through)은 동시 요청이 옛 값으로 덮어쓸 수 있어 기본으로 하지 않는다.
  - **삭제는 DB 커밋 뒤** — 트랜잭션 안에서 지우면 커밋 전에 다른 요청이 옛 값을 다시 채울 수 있다.
  - **짧은 TTL 은 안전망** — 삭제가 빠지거나 실패해도 옛 값이 남는 시간은 TTL 을 넘지 않는다. 그래서 회원 상태처럼 보안에 걸리는 캐시는 TTL 을 짧게 둔다.
  - **키는 한 곳에서 만든다** — 채우는 쪽과 지우는 쪽이 같은 util 함수로 키를 만든다(예: `auth-user:<login_scope>:<user_id>`).
  - **앱 경계를 넘는다** — 같은 데이터를 바꾸는 앱이 모두 같은 Redis 의 키를 지운다. 예: t_user 를 바꾸는 user-service · admin-service(매니저 · 관리자 도메인) · scheduler(탈퇴 완료).
  - **무효화 지점 목록을 함께 만든다** — 캐시 대상을 정할 때 그 데이터를 바꾸는 쓰기(service 메서드 · crontab · 다른 앱)를 빠짐없이 표로 만든다.
  - **테스트** — 무효화 지점마다 service spec 에서 캐시 포트 mock 의 삭제 호출 · 키 · 실패 경로의 미호출을 단언한다.
  - **Redis 장애** — 조회는 DB 로 넘어가 캐시 없이 동작한다.
- Scope: global
- Rationale: User feedback 2026-10-24 — "정지/탈퇴/수정 등의 행위가 이루어질 때, 캐시에 그 해당 회원에 대한 정보도 같이 수정해줘야겠지. 그런 전략을 메모해놔. 나중에 캐싱할 곳을 정할 때 도입해야함" (로드맵 Phase 23 — 캐시는 Redis, 결정 2026-10-24)
